# 위임 정책과 검증

WOMC의 위임 판단은 메인이 매 요청에서 하는 일회성 내부 자연어 판단이다. 외부 판단 엔진·API·훅·자동 분류기·상태 저장을 만들거나 사용하지 않으며, Python 생성기는 [정책 원본](../assets/delegation-policy.md)을 프로젝트 `AGENTS.md`에 넣을 뿐 작업을 자동 분류하거나 에이전트를 실행하지 않는다. 따라서 작업별 판단, 계획, 진행 기록과 과거 상태를 `AGENTS.md`에 누적하지 않는다.

## 적용 경로

[정책 원본](../assets/delegation-policy.md)은 생성 결과에 들어갈 유일한 기준표다. `setup_harness.py`가 내용을 루트 `AGENTS.md`의 WOMC 영역에 포함하므로 이후 프로젝트 세션에서 플러그인 캐시 경로를 다시 찾지 않아도 읽을 수 있다. 정책을 바꾸면 이 프로젝트 하네스도 재생성한다. 다른 프로젝트는 그 프로젝트의 WOMC를 갱신할 때 반영된다.

별도 범용 위임 스킬·모델 전환 훅·`config.toml`·사용자 정의 에이전트 파일을 만들지 않는다. 현재 도구의 모델·추론 인수를 사용하므로 세션 설정을 바꾸지 않고 위임 건마다 선택할 수 있다. 사용자가 지정한 조합·비용 상한·위임 금지와 기존 프로젝트 제한은 기본 기준보다 우선한다. 사용 가능 모델은 실제 환경에서 확인하며, 표를 계정의 지원 모델 목록이나 성능 보장으로 간주하지 않는다.

## 요청 판단 계약

메인은 먼저 요청을 서로 독립적인 작업으로 나누고 다음 값만 대화 안에서 사용한다.

| 대상 | 필수 값 | 뜻 |
| --- | --- | --- |
| 요청 | `readiness=ready` | 모든 작업을 지금 실행할 수 있다. |
| 요청 | `readiness=partial` | 아래 안전 계속 조건을 만족하는 일부 작업만 지금 실행할 수 있다. |
| 요청 | `readiness=blocked` | 실행 가능한 작업이 없거나 요청 전체가 막혔다. |
| 작업 | `status=ready` | 필요한 범위·근거·도구·승인이 갖춰졌다. |
| 작업 | `status=blocked` | 필요한 것이 없어 지금 실행하면 안 된다. |
| 실행 계획 | `planned_execution=direct` | 메인이 직접 수행한다. |
| 실행 계획 | `planned_execution=mixed` | 메인의 병행 작업과 서브에이전트의 독립 작업을 함께 쓴다. |
| 실행 계획 | `planned_execution=none` | 지금 실행하지 않는다. |

계획은 호출 성공, 실제 실행, 모델 선택 적용, 산출물 품질의 증거가 아니다. 현재 환경에는 서브에이전트만 수행하고 메인이 결과를 받기만 하는 `pure delegate`가 없다. 메인은 선택·범위 분리·통합·최종 검증·사용자 보고의 최종 책임을 계속 진다.

`ready`와 `partial`은 실행 가능한 작업이 있을 때 `direct` 또는 `mixed`를 쓰고, `blocked`는 `none`을 쓴다. `mixed`에는 준비된 위임 작업과 그 결과를 기다리지 않고 진행할 수 있는 메인의 유용한 병행 작업이 모두 있어야 한다.

`status=blocked`에는 반드시 (1) 막힌 작업 또는 범위, (2) 자연어 이유, (3) `needed_to_unblock`을 적는다. 이유는 사용자 입력 또는 명시적 승인 필요, 프로젝트 또는 사용자 정책상 금지, 결정·사실·출처 등 근거 부족, 필요한 파일·브라우저·서비스·권한 등 도구 접근 불가, 요청 모델·추론·도구 조합 또는 기능 미지원 중 하나로 구체화한다.

현재 권한과 도구로 범위 안에서 바로 해소할 수 있는 선행 확인은 차단으로 세지 않고 `ready` 작업의 실행 순서에 포함한다. 예를 들어 메인이 로컬 변경과 테스트를 직접 검증할 수 있으면 검증 뒤 통합하는 하나의 준비된 흐름이다.

`partial`은 차단된 작업과 실행 후보의 결과 및 의존성이 독립적이고, 후보가 되돌릴 수 있는 안전한 로컬 작업이며 사용자의 선택지를 좁히지 않을 때만 쓴다. 외부 변경, 배포, 푸시, 결제, 데이터 변경처럼 차단 해소 결과에 영향을 주거나 되돌리기 어려운 일은 계속하지 않는다. 조건이 하나라도 없으면 해당 작업은 `blocked`이고 계획은 `none`이다.

## 판단 시 주의할 차이

- 위임은 저렴한 모델 호출만으로 이득이 확정되지 않는다. 맥락 전달·대기·검토 비용을 함께 고려한다. 메인이 병행할 실질적인 작업이 있어야 하며, 빈 대기 시간을 만들기 위해 일을 나누지 않는다.
- 현재 대상 환경의 서브에이전트 도구는 유용한 메인 작업과 병행할 수 있는 독립 작업에만 생성을 허용한다. 그래서 독립 검토·맥락 절약의 가치가 있어도 병행 조건을 생략하지 않는다. 도구의 상위 제한이 달라진 환경으로 확장할 때 이 조건을 다시 검토한다.
- 기본 선호는 적극 위임이다. 독립 작업을 먼저 찾으며, 긴 전체 대화나 많은 파일 자체를 직접 처리의 이유로 삼지 않는다. 실제 전달할 맥락과 분리 가능성을 본다. 반대로 한 번의 검색이나 한 줄 수정은 파일 수가 많아도 직접 처리할 수 있다.
- 하나의 큰 요청에도 서로 다른 난도가 있다. 공개 문서의 사실 수집과 중요한 설계 판단을 분리하고 각각에 맞는 조합을 쓴다. 웹 조사·리뷰 같은 작업명이나 파일 수만으로 등급을 정하지 않는다.
- 사용자가 구현을 요청한 범위에서는 독립적인 파일 수정을 위임할 수 있다. 항상 메인만 코드를 쓰도록 제한하지 않는다. 변경 파일의 담당자를 정하고 메인이 통합 결과를 검증한다.
- 낮은 추론 수준으로 전부 시도한 뒤 차례대로 모델을 올리는 사다리를 강제하지 않는다. 처음부터 위험과 불확실성에 맞게 선택하고, 결과가 부족한 이유를 확인한 뒤 남은 부분만 재배정한다.
- 생성 요청에 모델과 추론 수준을 둘 다 전달해야 한다. 도구가 전체 대화 상속과 모델 변경을 동시에 허용하지 않으면 필요한 프로젝트 맥락을 독립 요청으로 넘긴다. 모델을 고정한 사용자 정의 역할은 호출 인수와 다르게 작동할 수 있으므로 현재 도구 규약과 역할 설정을 따른다.

## 컨텍스트와 위임 요청 최소 계약

서브에이전트도 자신에게 제공된 프로젝트·플러그인 스킬을 사용할 수 있다. 다만 메인이 읽은 스킬 본문, 전체 대화, 로그인 상태, 도구 접근이 언제나 동일하게 전달된다고 가정하지 않는다. 전달하는 컨텍스트는 정확하고 최소여야 한다. 적용 `AGENTS.md`와 필요한 스킬 이름·`SKILL.md` 진입 경로, 이 작업에 필요한 사실 요약, 대화에만 있는 제한을 빠뜨리지 않고 전달하되, 무관한 개인 정보·기록·긴 배경은 제외한다.

각 위임 요청에는 다음을 모두 포함한다.

1. 목표와 완료 기준
2. 프로젝트 루트, 담당 작업, 읽기·수정·제외 범위
3. 담당 경로에 적용되는 루트·중첩 `AGENTS.md`와 스킬 이름·`SKILL.md` 진입 경로. 지침 범위가 다르면 작업을 나눈다.
4. 확인한 사실과 아직 확인하지 못한 사실
5. 사용자 제약과 승인 상태: 예산, 허용/금지 모델, 동시 인원, 네트워크, 원격 푸시, 외부 변경
6. 필요한 도구와 실제 접근 가능 여부
7. 선택한 모델과 추론 수준, 선택 이유
8. 반환할 근거, 변경 파일/내용, 실행한 검증과 결과, 미확인·차단 사항

같은 파일이나 상호 의존적인 변경을 여러 담당자에게 중복 배정하지 않는다. 메인이 재위임을 별도로 허용하지 않으면 서브에이전트가 직접 수행한다. 서브에이전트는 적용 지침과 스킬을 직접 읽고, 읽을 수 없음과 필요한 도구 접근 불가를 구분해 메인에 알린다. 메인은 반환된 근거·변경·검증·미확인을 검토한 뒤 통합하고 최종 결과를 보고한다. 다른 모델을 고르는 것으로 권한 문제가 해결된다고 판단하지 않는다.

## 실패와 재시도

| 원인 | 허용 재시도 | 후속 처리 |
| --- | --- | --- |
| 권한 거부, 정책 금지, 확정된 미지원 | 0회 | 차단 이유와 `needed_to_unblock`을 보고한다. 다른 모델로 우회하지 않는다. |
| 일시 도구 오류 | 1회 | 같은 호출을 한 번만 다시 시도하고, 실패하면 차단한다. |
| 근거 누락 또는 불완전한 반환 | 1회 | 필요한 근거만 좁혀 보완 요청하고 다시 부족하면 차단한다. |
| 추론 부족 | 1회 | 실패한 전체 작업을 반복하지 말고 미해결 범위만 다시 판단해 적합한 조합에 재배정한 뒤 메인이 검토한다. |

숫자 신뢰도, 점수, 임계값으로 위임 여부나 결과의 신뢰성을 꾸미지 않는다. 근거가 부족하면 그 사실과 필요한 입력을 자연어로 적는다.

## 검증

생성기 검사에서는 새 생성·기존 갱신·반복 실행, 사용자 설정과 지침 보존, 미리보기의 무변경을 확인한다. `--check` 통과는 정책이 생성 결과에 포함됐다는 뜻이지 실제 위임 품질의 증명이 아니다.

정책의 판단 품질은 서로 독립적인 다음 상황으로 확인한다. 평가 에이전트에는 정책 원본과 요청만 주고, 기대 모델이나 의심하는 결함을 미리 알려 주지 않는다. 실제 작업을 실행하지 않는 판단 검사는 모의 검증으로 보고한다.

- README의 짧은 오타 하나 수정
- 메인이 호환성 분석을 하는 동안 공개 문서에서 지원 옵션을 확인
- 서로 모순된 출처를 대조해 보안 관련 설계 판단을 지원
- 서로 겹치지 않는 구현 두 부분과 최종 통합
- 사용자의 특정 모델 제외 또는 위임 금지
- 요청한 모델 미지원, 브라우저 권한 거부, 근거 없는 답변
- 프로젝트 스킬이 필요하지만 전체 대화 상속은 사용할 수 없는 상황

실제 실행을 검증할 때는 호출에 지정한 모델·추론과 도구가 확인해 준 정보, 스킬을 읽은 증거, 반환된 결과를 각각 확인한다. 호출 성공만으로 모든 모델·클라이언트의 동작이 증명되지는 않는다. 계정·네트워크를 쓰는 별도 Codex 통합 검사는 기존 선택형 절차를 따른다.

여러 차수의 검증·수정을 요청받으면 차수마다 정책 사본과 새로운 상황을 평가자에게 전달한다. 기대 판정은 응답 전에 따로 기록하고 평가자에게는 주지 않는다. 실제 응답과 판정을 보존한 뒤 필요한 수정만 다음 사본에 반영한다. 잘못된 선택이 없으면 그렇게 기록하며, 횟수를 채우려고 결함이나 개선 성과를 만들지 않는다. 마지막 차수에는 앞선 경계와 새 상황을 함께 검사한다. 모의 선택이 맞았다는 사실과 실제 위임 실행·비용·품질은 구분한다.
