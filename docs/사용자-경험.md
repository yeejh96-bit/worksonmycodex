# WOMC 사용자 경험

## 제품 약속

WOMC는 사용자가 만들고 싶은 것과 되돌리기 어려운 결정에 집중하도록 한다. Codex는 프로젝트를 읽고, 필요한 하네스를 만들고, 작업하면서 알게 된 지속 정보를 다음 작업에 남긴다. 사용자는 WOMC 명령과 에이전트 설정을 일상적으로 관리하지 않는다.

## 대표 사용자 페르소나

### 민지 — 제품은 만들고 싶지만 에이전트 설정은 관리하고 싶지 않은 사람

- 만들고 싶은 제품과 사용자 문제는 설명할 수 있다.
- 저장소 구조, 테스트 명령, `AGENTS.md`, 스킬의 차이는 잘 모르거나 매번 기억하고 싶지 않다.
- 설치할 때 한 번 정도의 명령과 훅 검토는 받아들일 수 있다.
- 일상 작업에서는 Codex가 합리적인 세부 결정을 내리고 구현과 검증까지 끝내기를 기대한다.
- 삭제, 배포, 결제, 운영 데이터 변경처럼 되돌리기 어려운 결정만 직접 확인하고 싶다.
- 새 문서나 스킬을 만들 때마다 `AGENTS.md`를 손으로 동기화하고 싶지 않다.

민지의 성공 기준은 “Codex를 열고 원하는 기능을 말하면, 지난 작업에서 정해진 프로젝트 맥락과 필요한 문서를 이미 알고 끝까지 작업하는 것”이다.

## 경험 원칙

1. 설치 이후에는 WOMC 자체를 호출하지 않아도 된다.
2. 프로젝트에 이미 있는 코드와 문서로 알 수 있는 것은 사용자에게 묻지 않는다.
3. 목표와 범위가 충분하면 Codex가 조사·계획·구현·검증·보고를 이어서 수행한다.
4. `AGENTS.md`에는 다음 작업의 결과를 바꾸는 지속 정보만 둔다.
5. 긴 배경은 `docs/`, 반복 절차는 스킬, 경로별 제약은 가장 가까운 중첩 `AGENTS.md`에 두고 루트에는 사용 조건과 진입 경로만 둔다.
6. 현재 작업의 계획·진행 상황·완료 기록은 하네스에 쌓지 않는다.
7. 되돌리기 어려운 결정과 프로젝트 목표를 바꾸는 선택만 사용자에게 묻는다.

## 사용자 흐름

### 1. Git 마켓플레이스 등록과 설치

민지는 한 번만 Git 마켓플레이스를 등록한다.

```sh
codex plugin marketplace add yeejh96-bit/worksonmycodex --ref main
```

그다음 `/plugins`에서 `WOMC`를 검색해 설치한다. 새 세션에서 `/hooks`를 열어 `SessionStart` 훅을 검토하고 신뢰한다.

기대 결과: 이후 프로젝트마다 설치 명령이나 `/womc` 같은 초기화 명령을 입력하지 않는다.

### 2. 첫 프로젝트 열기

민지가 프로젝트 루트에서 Codex를 시작하면 훅이 루트 `AGENTS.md`를 검사한다.

- 하네스가 없으면 모델이 첫 요청을 처리하기 전에 WOMC를 적용한다.
- 기존 프로젝트면 README, 지속 문서, 매니페스트, 로컬 스킬과 검증 설정을 조사한다.
- 빈 프로젝트라서 목적을 알 수 없을 때만 무엇을 만들지 묻는다.
- 비어 있지 않은 `AGENTS.override.md`나 깨진 WOMC 마커가 있으면 덮어쓰지 않고 충돌을 설명한다.

기대 결과: 루트 `AGENTS.md`에 자율 실행 원칙과 프로젝트 브리핑이 생긴다.

### 3. 프로젝트 브리핑 형성

WOMC는 코드만으로 다음 작업에 충분하지 않은 정보를 골라 기록한다.

- 프로젝트 목적: 무엇을 누구를 위해 만드는지 한 문장
- 변하지 않는 제품 원칙과 보안·승인 경계
- 여러 작업에 계속 적용되는 완료 기준
- 작업 상황별로 먼저 읽을 문서와 사용할 스킬
- 실제로 실행할 수 있는 공통 검증 명령

예시는 다음과 같다.

```markdown
### 프로젝트 목적
팀이 로컬 문서를 안전하게 정리하고 검색하도록 돕는 앱이다.

### 작업별 문서·스킬 경로
- 모든 구현 작업 전에 `docs/product-principles.md`를 읽는다.
- 결제 정책이나 요금제를 변경할 때는 `docs/billing.md`를 읽는다.
- 릴리스 후보를 만들거나 배포 전 검증을 할 때는 `skills/release-helper/SKILL.md`를 읽고 스킬을 따른다.
```

기대 결과: 긴 내용을 매번 프롬프트에 넣지 않아도 Codex가 상황에 맞는 진입 경로를 안다.

### 4. 일상적인 기능 작업

민지는 “검색 결과를 태그로 필터링하게 해줘”처럼 결과만 요청한다. Codex는 시작할 때 읽은 `AGENTS.md`에 따라 관련 문서와 스킬을 불러오고, 안전한 범위에서는 추가 승인 없이 구현과 검증을 마친다.

기대 결과: 사용자는 하네스를 운영하는 대신 제품 결정을 내린다.

### 5. 프로젝트가 배우고 변하는 과정

작업 중 다음 변화가 생기면 같은 작업을 끝내기 전에 하네스를 갱신한다.

- 다음 작업에도 영향을 주는 제품 사실이나 제약을 새로 알게 됨
- 프로젝트 수준 완료 기준이나 검증 명령이 바뀜
- 반복 절차를 로컬 스킬로 만듦
- 반드시 읽어야 하는 긴 근거 문서를 추가하거나 역할을 바꿈
- 새 앱·패키지·서비스 같은 워크스페이스 영역을 추가함

Codex 밖에서 문서나 매니페스트가 바뀐 경우에는 다음 세션의 컨텍스트 스냅샷 검사가 변화를 감지한다. 모델은 내용을 검토하고 전역 읽기 경로인지, 특정 작업의 읽기 경로인지, 스킬 안에 둘 참고 문서인지 판단한다.

일반 소스 코드 수정은 하네스 갱신을 일으키지 않는다.

기대 결과: `AGENTS.md`는 고정된 초기 파일이 아니라 프로젝트와 함께 다듬어지는 짧은 브리핑이 된다.

### 6. 플러그인 갱신

Git 마켓플레이스가 새 버전을 받으면 WOMC는 골격 버전을 비교한다. 프로젝트 골격이 오래되었으면 다음 세션 첫 요청 전에 최신 형식으로 갱신하되, 프로젝트 목적·지속 제약·완료 기준·수동 읽기 경로와 검증 명령을 보존한다.

## [`works-on-my-claude`](https://github.com/yeejh96-bit/works-on-my-claude)에서 가져온 것과 Codex에 맞춘 것

가져오는 핵심은 설치 후 자동 설정, 프로젝트 브리핑, 작업 중 알게 된 지속 정보의 자율적인 반영, 긴 근거와 짧은 진입 지침의 분리다.

Codex에서는 다음처럼 적용한다.

- `CLAUDE.md` 대신 [Codex가 작업 전에 읽는 `AGENTS.md`](https://learn.chatgpt.com/ko-KR/docs/agent-configuration/agents-md)를 사용한다.
- `.claude/rules` 대신 적용 경로에 가장 가까운 중첩 `AGENTS.md`를 사용한다.
- 권한 파일을 별도로 생성하지 않고 현재 Codex 샌드박스와 승인 정책을 따른다.
- 모든 작업에 고정 단계, 체크포인트 커밋, 별도 서브에이전트 검증을 강제하지 않는다.
- 목표가 명확하면 Codex가 현재 환경과 작업 위험에 맞는 방법을 선택해 완료까지 지속하도록 한다.
- 현재 계획과 진행 기록은 `AGENTS.md`에 저장하지 않는다. 장기 작업 상태는 Codex의 작업·목표 기능이나 프로젝트의 기존 작업 관리 방식을 사용한다.

## 출시 확인 기준

- 새 프로젝트의 첫 요청 전에 루트 `AGENTS.md`가 생성된다.
- 기존 프로젝트에서는 코드로 알 수 있는 사실 때문에 불필요하게 질문하지 않는다.
- 로컬 스킬의 `description`이 사용 조건과 `SKILL.md` 진입 경로로 기록된다.
- 긴 근거 문서는 전역 또는 작업별 조건과 함께 읽기 경로로 기록된다.
- 시작 문서나 매니페스트의 내용 변화가 다음 세션에서 감지된다.
- 일반 소스 코드 변경만으로 `AGENTS.md`가 바뀌지 않는다.
- 수동으로 남긴 프로젝트 목적·원칙·승인 경계·완료 기준·읽기 경로·검증 명령이 자동 갱신에서 보존된다.
- 회의록·구현 일지·변경 기록이 지속 지침으로 누적되지 않는다.
